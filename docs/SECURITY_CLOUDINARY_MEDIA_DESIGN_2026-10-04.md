## 2. Data flow and client behavior

```text
Flutter picker / avatar crop
  → authenticated multipart POST /api/media/upload (file + context)
  → auth/onboarding → rate limit → Multer MIME/size filter
  → unconfigured: local disk + public /uploads URL
    configured: signed backend SDK upload_stream → provider public ID + URL
  → response {url, thumbnailUrl, publicId, fileName, fileSize, mimeType, dimensions}
  → second HTTP write stores URLs/metadata in Message, User avatar or Handoff
  → permitted REST/socket readers receive references
  → Flutter fetches image/video/document URL separately
```

`medcollab-app/lib/features/media/data/repositories/media_repository.dart` uploads bytes to Vocle through authenticated `ApiClient`; it has no direct Cloudinary operation and no delete method. `MediaUploadResult` retains publicId temporarily, but message/thread repository serializers send only URLs and content metadata. Channel/thread cubits upload then send; a failed send leaves a completed upload. Profile page uploads `avatar.jpg` with context avatar then updates `/users/me`; it does not delete the old asset or compensate if the profile write fails. No handoff media-upload UI invocation was found; handoff attachment storage is a real backend sink and `context=handoff` is an exposed backend upload option, not proof of a completed Flutter handoff flow.

Picker options exceed backend types (e.g. doc/docx/txt, GIF/MKV), a compatibility gap rather than a new authorization defect. Images use network/cache widgets; `DocumentOpenService` uses a separate Dio client to download the supplied URL on mobile and launches it on web/external fallback, without Vocle authentication. These are client retrieval trust boundaries. Backend URL validation/storage does not fetch URLs and is not evidence of SSRF. Never open canary foreign URLs during tests.

Client-controlled inputs: bytes, claimed MIME, original filename, context; delete publicId; all reference URLs/thumbnail/filename/MIME/size/dimensions and handoff uploadedAt. Server controls authenticated user ID and folder mapping. Client `userId`, `spaceId`, `folder`, `public_id`, `resource_type`, `overwrite`, `transformation`, `upload_preset` must be tested as ignored/rejected inputs, not assumed SDK parameters.

## 5. Test architecture and evidence contract

Proposed paths (not created in this phase): `medcollab-backend/scripts/security-media/{run-local,run-contract,run-live,guard,broker,journal,report}.js`, fixture and scenario modules beside them; proposed workflows `.github/workflows/vocle-media-security-local.yml` and `vocle-cloudinary-security-integration.yml`. Keep reports/IDs separate (`MEDIA-LOCAL-*`, `MEDIA-CONTRACT-*`, `MEDIA-CLOUD-*`, `MEDIA-CONFIG-*`); the matrix labels below are design requirements, not registered/executed case counts. Do not modify the 691-case manifest or reinterpret its results.

1. **Local boundary lane:** real loopback Express/Mongoose, disposable MongoDB, dedicated scratch working directory/upload tree; all providers absent and outbound traffic blocked. Reuse fixture/access helpers carefully, without automatically rerunning the generic suite.
2. **Offline contract lane:** load unchanged controller/config code in a separate process using a test-only module adapter and SDK spies. Capture exact upload/delete/URL options and stream bytes; use clearly labeled simulated results/errors. No real credential material and zero external networking. This proves application SDK intent/callback behavior only, never Cloudinary enforcement. Also test the real installed URL builder without keys under an explicitly cleared SDK configuration.
3. **Optional live lane:** an isolated backend uses a test-only config/SDK adapter to a loopback credential broker. The broker alone owns approved test credentials and external access. It validates application options before translating folders to the run namespace and forwards real buffer uploads. Local MongoDB and all other disabled providers remain mandatory. Separately label broker-enforced isolation, original application behavior and actual provider responses. Safety denial at the broker is not proof that the application authorized correctly.
4. **Configuration lane:** static structured checks and sanitized, owner-provided test-environment attestation. No production queries and no Console settings mutations. Treat absent evidence as unverified, not PASS.

Every case needs a legitimate control; exact denied response plus relevant disk/provider/DB/adapter state; persisted successful reference and allowed-reader evidence; cleanup outcome; requested/original/effective provider options where applicable. Record sanitized fixture labels, booleans, resource type, MIME, size/hash, status, opaque IDs and report hashes. Never record tokens, authorization/signature headers, secrets, raw request/response bodies or download contents. Missing control, 429 preventing execution, provider authentication error, fixture failure, unsafe cleanup, transport failure or incorrect cloud identity is an **infrastructure failure**, not an application pass/observation. Provider decoding rejection is a test outcome only after successful environment and valid-file controls.

Known application observations remain non-gating until separately reviewed remediation and policy approval; safety guards are strict from first implementation. Gate labels below mean eventual eligibility, not activation now. Do not assert safety by weakening expectations to current vulnerable behavior.

**Preferred: a separately administered Cloudinary account containing only synthetic security-test assets, with a dedicated product environment and distinct key pair.** A folder in the production environment is unacceptable. A separate staging product environment is an alternative only after its keys and administrators are shown to have no production/account-management scope; a standalone test account is simpler to audit. No credentials are necessary to implement local/contract/config guard tests. Request provisioning only when those guards pass and live behavior is the next authorized step.

Cloudinary documents product environments as separate asset repositories/settings ([glossary](https://cloudinary.com/documentation/cloudinary_glossary)). Its current [permissions guide](https://cloudinary.com/documentation/dam_admin_permissions) distinguishes migrated Roles and Permissions from legacy permissions, supports API-key role assignment and cautions that root keys have full scope; custom roles depend on plan. Do not rely on the older [credential FAQ](https://cloudinary.com/documentation/developer_onboarding_faq_find_credentials), which still describes granular keys as forthcoming, to promise or deny a permission feature. Verify the **test account's** actual system and available scope at provisioning. Folder-level authorization is defense in depth, not the production-isolation mechanism.

### Minimum access

Broker needs signed Upload API buffer upload and exact-resource destroy for image/video/raw; authenticated Admin API read of the exact marker and registered resource metadata, plus tightly scoped prefix reconciliation only for pending operation folders with lost responses. It needs no preset/config changes, account provisioning, usage/global search, rename, bulk/prefix deletion or real-user access. Use a non-root key with the smallest supported environment/folder roles; attest effective permissions rather than assuming upload-only/read-only labels. If the plan only provides a broader environment key, it may be used **only in the standalone synthetic-only account**, with documented limitation and broker/network restrictions; never solve permission limits by using a production/root/account-management key. No separate verification key is required if the dedicated pair provides those reads; if separation is available, a marker/resource-read key is optional, also test-only and broker-held.

### Fail-closed sequence and trust model

The design protects against accidental production configuration and buggy tests, not a malicious administrator deliberately replacing approved policy/credentials/network controls. These controls are proposed and must be implemented/tested before any live run; this document itself is not an enforced guarantee.

1. Use a disposable checkout/container with no .env or credential files. Local runner/backend receives no provider secret. Clean allowlisted environment, exact loopback DB/API and disabled unrelated providers are checked before imports; network sandbox denies external access to backend/test process. No application `server.js` with dotenv starts on the host. Module adapter remains test-only, source hashes unchanged.
2. Broker checks trusted policy digest, authorized repository/master/workflow, explicit live mode, exact cloud-name equality, and key-identifier fingerprint **before constructing SDK clients or making even a read**. Expected identity cannot be supplied by the same untrusted dispatch input as actual identity. Missing marker/policy/secret means blocked. Never try production names to compare credentials; never echo key/secret/fingerprint diagnostics beyond match booleans.
3. Broker network egress permits only HTTPS to the pinned Cloudinary API regional host and validated requests whose cloud path is the approved test name. Ignore SDK/env endpoint overrides. Method/operation allowlist: exact marker/resource reads, buffer upload, exact-ID destroy; no fetch/remote file URL, unknown SDK method, search-all, folder/prefix deletion, provisioning, settings or arbitrary URL. DNS/TLS validation stays enabled and redirects are rejected. Generic GitHub runner outbound access alone is insufficient: broker must enforce path and request semantics, and backend cannot bypass it.
4. Before a write, authenticate an exact read of the pinned non-production marker and compare immutable asset identity plus pinned marker metadata. Record only match booleans. Failure terminates without alternate config/fallback. This positive provider evidence supplements the independent cloud/key policy; `/health.cloudinary=true` is not an identity attestation.
5. Generate run root `vocle-security/<run-id>-<attempt>-<uuid>/<shard>` solely in the trusted harness. Each operation gets an independent child folder. Adapter first validates/captures the application's original folder and options, then broker prefixes that folder under the run root (preserving `medcollab/messages/<actor>` etc.). It rejects dot segments, backslashes, empty/encoded separators, escapes and unregistered IDs. **The original backend has no test-prefix setting**, so merely setting an env folder is insufficient. Translating folders is a test transport adaptation, not a production fix or exact proof of deployed namespace behavior.
6. Generated filenames/IDs use random synthetic labels with no phone, patient data or real identity. Preserve original naming options for provider-naming probes; deterministic provider-only fixtures use explicit pre-journaled IDs and are reported separately. Dynamic-folder mode needs explicit asset-folder/public-ID-prefix treatment based on approved mode. If legacy folder option cannot safely yield the expected public-ID prefix, abort and implement a reviewed transport mapping; do not silently credit application compatibility. [Folder mode documentation](https://cloudinary.com/documentation/folder_modes) explains the distinction.
7. Validate returned IDs, asset IDs, type and secure URL before returning them to backend or fetching. CDN egress is restricted to HTTPS `res.cloudinary.com`, the exact approved cloud, exact registered resource and approved bounded transformation grammar. No credentials/ports/query redirects, other clouds, overlays/remote-fetch URLs or arbitrary transformation chains. Wrong-cloud URL strings are test data only and never fetched. Delivery redirect rejection applies to every request. Originals and each derived URL are validated separately.
8. Application calls to delete are logged for authorization assertions, but broker destroys only exact resources recorded for this run, cloud, resource type and delivery type. Guard denial is safety evidence; it cannot turn an application ownership defect into a PASS. Marker and other runs' canaries are outside the mutation set. Only the broker janitor may reconcile a pending child-operation prefix; it never lists another cloud or an arbitrary caller prefix.

A prefix alone, GitHub secret masking, a test-mode flag, separate URLs, a health boolean or a caller-populated EXPECTED_CLOUD value is not sufficient. Production read safety includes the public CDN: other-cloud references cannot be fetched even without credentials. Dedicated account, independent positive identity binding, credential separation, network restrictions and exact-resource inventory together prevent tests from targeting production within this trust model.

## 10. Cleanup, failure and concurrency

Before each provider upload, persist a credential-free intent journal: approved cloud binding, run/operation namespace, original/effective SDK options, synthetic owner, resource type/delivery type and pending state. Once upload succeeds, fsync returned publicId/assetId/version and allowed delivery URLs before subsequent actions. Use independent operation folders so a lost response can be reconciled safely without relying on generated IDs. Tag metadata, if added by broker, is harness instrumentation and not existing application behavior.

Normal cleanup runs in finally and workflow `if: always()`, using exact journaled IDs/type/delivery type and `invalidate:true` for test cleanup. Do not use `delete_resources_by_prefix`, delete-all or a user-supplied folder. Check absence with an exact authorized resource query; keep bounded CDN checks distinct from origin absence. Signed/raw deletion uses the recorded identity, not image→raw guessing. Marker is permanently excluded. Cleanup of a test-created foreign actor canary happens only after ownership assertions.

Pending/lost-response intents can list only the specific pre-registered operation prefix in the approved test environment, with page/count bounds. A reconciliation result must match prefix, upload time and operation correlation before exact-ID destroy. Ambiguous/unmatched results stay untouched and require owner review. If naming or folder mode cannot guarantee this scoping, live uploads are blocked until deterministic intent naming or equivalent safe reconciliation is available. Never declare successful cleanup from a 200 HTTP envelope alone.

Cancellation/process loss can prevent finally/always from running. Preserve the nonsecret journal as an artifact and require a separately reviewed test-only janitor/manual recovery path with the same environment identity guards, validated original journal and namespace. No new scheduled automation is created here. Do not claim crash-proof deletion from hooks alone. Orphan budget/age limits and unresolved-cleanup status block the next live run; stop further writes on quota/rate/auth failure. Define small per-run asset/byte/transformation/request ceilings before enabling the workflow.

Concurrency root contains run ID, attempt, UUID and shard; include unique synthetic user IDs. A ledger lock/lease prevents concurrent cleanup of the same run; janitor processes a stale manifest only after lease/age checks. Initial live suite runs serially. Different runs never clean one another's namespace. Database/file fixtures also have disjoint IDs/roots; do not reuse generic discovery's DB concurrently. Local cleanup resolves absolute scratch targets, verifies root/owner containment and rejects symlinks/junctions before any unlink or recursive removal. Cleanup invariants are strict even while application findings remain observations.

Provider deletion and CDN invalidation are separate. Cloudinary's [Upload API reference](https://cloudinary.com/documentation/image_upload_api_reference) documents signed SDK requests, overwrite defaults and optional invalidation; no instant cache-erasure guarantee should be encoded. Application source currently omits overwrite false and invalidation. [Account security settings](https://cloudinary.com/documentation/developer_onboarding_faq_account_security) documents strict transformations. [Media access control](https://cloudinary.com/documentation/control_access_to_media) distinguishes protected originals/derived assets; a signed delivery URL alone should not be assumed to expire or grant application membership semantics. These public documentation pages were reviewed; no Console, API or media resource was accessed during this design.
