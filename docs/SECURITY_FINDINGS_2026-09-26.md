## Authorization model used

Protected resource routes use `middleware/auth.js:protect` (JWT signature/expiry, existing active user) and generally `requireOnboarding`. The `User.role` medical role does not grant a `Space.members.role` admin role. `Space.isMember/isAdmin` and `utils/channelAccess.js` establish public-space membership, private-channel member/admin access, explicit DM membership and archived-channel denial. ObjectId validation and Mongoose `ref` fields do not enforce ownership or parent/child binding.

Current `utils/knownUsers.js` explicitly distinguishes discovery from messaging: same institution allows discovery, **not automatic DM creation**. Existing active DM or accepted request permits messaging; shared active space or target opt-in permits a request. `createOrGetDM` intentionally supports one-member self notes. Handoff model/submit behavior establishes draft privacy from ordinary receivers and unrelated members; admin audit access is a separate documented exception and is not tested by the four draft observations.

## Socket null-status and harness audit

All 21 socket cases completed: 12 pass, nine observations. `security-api-discovery.js:execute` deliberately records socket `actual.status=null`, separately `healthStatus=200`; the suite's `run` awaits event work then calls `/health`. `passed` uses the health response and semantic invariant. In all nine observations `authorizedControl=true`, `invariantHeld=false`, and matching unauthorized packets were captured. Counts: 339/340 = one each; 342/343/345/346 = two each; 347/348/349 = one each. No timeout, transport error or missing-control path accounts for them. They confirm S7–S9, not nine unresolved failures.

The report formatter misleadingly prints “expected 200, got null” and generic ambiguity/manual flags because it reuses HTTP expectations. That is a reporting defect affecting presentation, not the security verdict. Future reporting should show expected invariant, control result, event evidence and health separately. Never change socket status to an invented HTTP success. The once helper rejects missing controls; the runner marks unexpected execution errors as infrastructure failures. `stateUnchanged` on socket cases includes deliberate scenario mutations and is not an authorization verdict.

Additional coverage-quality limits: 159/268/272/273 need sanitized returned-ID/field evidence, not raw response bodies; 223/224 blocked-request passes can be masked by the earlier opt-in gate; side-effect snapshots exclude complete User/OTP/SupportTicket state; typing member cache survives fixture resets. These require targeted stronger preconditions/checks, not retrospective pass claims. Existing exact canary and attacker attribution make the current socket positives usable despite those limits.

## Higher-risk uncovered source findings (outside the 40)

**P0 investigation — MSG91 signature verification bypass.** `auth.routes.js` publicly mounts POST `/api/auth/verify-msg91-token`; validators require phone/token shape. `auth.controller.verifyMsg91Token` trusts `msg91Widget.service.verifyWidgetAccessToken`, which checks only that MSG91_AUTH_KEY is nonempty, decodes a phone from a JWT-shaped payload and returns success at lines 159–162 without signature/issuer/audience/expiry verification or provider call. Controller can then issue application tokens for that phone via `issueAuthTokensForPhone`. This is a concrete source-level authentication defect; **no HTTP exploit was executed in this review or among the 352 cases**, and deployed configuration was not inspected. Prioritize isolated route confirmation with a dummy non-secret key and outbound network blocked; do not call MSG91. Keep this separate from the nine roots confirmed by hosted cases.
